# go-moex — план переработки под боевую маркетдату и торговлю Sleipnir

Дата: 2026-09-02. Основание: сверка кода v1.0 (коммит `edad20a`) с первичкой
биржи — `simba_spectra-9.0.xml`, `spectra_simba_en.pdf` (ред. 10.04.2026),
`spectra_fixgate_en.pdf` (ред. 20.11.2025), `twime_spectra-7.7.xml`,
эталонный `PythonSimbaClient-9.0` и `prod/primary/configuration.xml`.
Локальные копии первички: `~/artefacts/moex-specs/`. Все файлы лежат на
`https://ftp.moex.com/pub/{SIMBA,TWIME,FIX}/Spectra/` (через наш прокси
нужен `curl -k`: цепочка TLS ломается на прокси).

Документ — рабочий план, а не ревью: сначала фиксируем, что подтвердилось
из внешнего вердикта и что добавилось, затем целевая архитектура и этапы.

### 1.2. Чего в вердикте нет (найдено при сверке)

| # | Дефект | Тяжесть | Первичка |
|---|---|---|---|
| N1 | **Фрагментация снапшота не обрабатывается.** `loadOrderBookSnapshot` вызывает `Engine.LoadSnapshot` на каждый пакет; снапшот инструмента приходит несколькими пакетами (`StartOfSnapshot` … `EndOfSnapshot`), значит в книге останется только последний фрагмент | блокер (проявится сразу после починки V2) | §1.4.8; `MsgFlagsSet` в XML: «first/last message in the snapshot for the instrument» |
| N2 | **Нет фильтра OTC-заявок.** В книгу активных заявок нельзя класть записи с флагом `NonQuote` (0x4) — ни из инкрементов, ни из снапшотов. `MDFlags` в `forts/` не читается вообще | высокая: адресные/внебиржевые заявки и сделки попадут в книгу и в «сделки» | §4.2.9 |
| N3 | **SequenceReset игнорируется.** `Decoded.NewSeqNo` в `forts/` не потребляется. После ежедневного сброса (00:00–05:50 МСК) `RptSeq` начинается с 1, строгая проверка `seq == last+1` даёт `ErrSequenceGap` на каждом сообщении → `Clear()` на каждом сообщении, книга мертва до рестарта процесса | высокая (каждый день) | §4.2.7 |
| N4 | **`ErrUnknownOrder` → `Clear()` всей книги.** Любое `Delete` заявки, которой нет в движке, стирает всё. Сегодня (без снапшота) это первая же отмена заявки, выставленной до нашего подключения, т.е. секунды после старта. Со снапшотом — любая рассинхронизация превращается в полную потерю книги без ресинка | высокая | — |
| N5 | **Дубликат = гэп.** `seq <= lastSeq` трактуется как `ErrSequenceGap` → `Clear()`. Для A/B-дедупликации и наложения Replay-хвоста дубликаты должны молча отбрасываться | средняя (блокирует V3) | §1.4.2, §4.2.6 |
| N6 | **Непрерывность `RptSeq` не гарантирована спекой.** В официальном примере §4.2.1 подряд идут RptSeq 60142 → 60144 → 60145. Либо опечатка в доке, либо часть обновлений (например, NonQuote) в поток не попадает. Проверяется только на pcap; если разрывы штатны — гэп-детекция строится на `MsgSeqNum` пакета, а `RptSeq` проверяется на монотонность, не на +1 | неизвестно, решает pcap | §4.2.1 |
| N7 | **Семантика EmptyBook неоднозначна.** §4.2.8 описывает три глобальных варианта (различаются по `ExchangeTradingSessionID` и `LastMsgSeqNumProcessed`), после которых книги приходят заново как OrderUpdate с `PossDupFlag`. Но §4.2.2 показывает EmptyBook внутри пакета транзакции по одному инструменту. У сообщения нет `SecurityID`. Текущий код чистит движок на любой EmptyBook — для многоинструментного потребителя это стирание чужой книги без ресинка. Пункт 8 handoff («грубее, чем позволяет спека») неточен: спека сама противоречива, нужна эмпирика | средняя, решает pcap | §4.2.2, §4.2.8 |
| N8 | **Нет защиты от смены схемы.** `SchemaID`/`Version` парсятся и не проверяются, `MsgSize` не сверяется с длиной датаграммы. Бамп схемы (9 → 10, как было 8 → 9 в феврале 2026 со сменой id сообщений 21→27, 9→28) даст тихий мусор в книге вместо ошибки | средняя, копеечная правка | §2.3.3, §2.3.5, история изменений спеки |
| N9 | **Join без указания источника.** `net.ListenMulticastUDP` делает ASM-join. В `configuration.xml` у каждой группы есть `src-ip`, эталонный клиент биржи делает `IP_ADD_SOURCE_MEMBERSHIP` (SSM). В колокации ASM может не отдавать трафик; нужен SSM-join (через `golang.org/x/net/ipv4` или прямой `setsockopt`) | средняя, проверится только на площадке | `app_multicast_decoder.py`, `configuration.xml` |
| N10 | `Engine.Clear()` не сбрасывает трекер `seq`; `LoadSnapshot` при неполном снапшоте (N1) молча даёт неверную книгу | связано с N1/N3 | — |
| N11 | Тесты — только синтетика на один пакет = одно сообщение; нет теста на пакет с несколькими сообщениями, на фрагменты снапшота, на последовательность пакетов | — | — |
| N12 | `go.mod`: `shopspring/decimal` помечен `// indirect`, хотя импортируется напрямую — `go mod tidy` в CI не гоняется | косметика | — |

### 1.3. Уточнения к формулировкам вердикта

- «после первого гэпа книга пуста навсегда» — точнее: `Clear()` не трогает `lastSeq`, следующее сообщение с `last+1` применяется, книга частично отстраивается из новых заявок и снова стирается на первой же отмене старой (N4). Итог тот же — книга никогда не верна, — но механика другая, и чинится это не только снапшотом.
- Гэп-стратегия handoff §5.6 («ждать следующего цикла снапшотов») — не «медленное восстановление», а несуществующее: Snapshot-поток не подписан (V2).
- TCP Replay — не опция, а часть штатного восстановления при малых потерях; спека ограничивает: ≤1000 сообщений в запросе, 2 одновременных соединения, 1000 соединений/сутки с IP, таймаут активности 1 с.
- Прод-адреса из `configuration.xml` (для конфига): ORDERS-LOG Incremental A `239.195.20.81:20081` (src `91.203.253.244`), B `239.195.148.81:21081` (src `91.203.255.244`); Snapshot A `239.195.20.82:20082`, B `239.195.148.82:21082`; Replay TCP `91.203.255.244:7029`; FUT-INFO Replay/Incremental `…20.83:20083` / `…20.84:20084` (+B `…148.83/84`). У `SIMBAConfig` сейчас одна пара Instruments-групп, а по спеке два потока (Instrument Replay и Instrument Incremental) и отдельно FUT-INFO/OPT-INFO.

## 2. Целевая архитектура SIMBA-части

Слой `internal/simba` остаётся протокольным, `orderbook` — движком, `forts/`
— доменом (принципы handoff §2 сохраняются). Меняется содержимое.

### 2.1. `internal/simba` — декодер и транспорт

- **`Packet` как flyweight поверх `[]byte`**: аксессоры заголовков и
  итератор сообщений `Next() (hdr SBEHeader, body []byte, ok bool)`, шаг —
  `BlockLength` + размер групп по `groupSize`. Ноль аллокаций: ни
  указателей, ни `make`. Сообщения — value-структуры (50–74 байта копировать
  дешевле, чем аллоцировать), группы обходятся по индексу
  (`Snapshot.Entry(i)`, `BestPrices.Entry(i)`), а не собираются в слайс.
- **Guard**: `SchemaID == 19780`, `Version` из конфига (по умолчанию 9),
  `MsgSize == len(datagram)`; несовпадение — счётчик + ошибка наверх, не
  тихое продолжение.
- **`Listener`**: SSM-join по `src-ip` (N9), `SO_RCVBUF` из конфига, чтение
  в переиспользуемый буфер, обработчик на read-горутине (как сейчас).
- **`Feed`** (новое): объединяет A+B одного канала, ведёт `MsgSeqNum`:
  `seq <= last` → дубликат, отбросить; `seq > last+1` → гэп, событие
  наверх с диапазоном; `SequenceReset` → `last = NewSeqNo-1` и событие
  «сброс». Один общий трекер на пару A/B (у пары общий счётчик, §1.4.6).
- **`Replay`** (новое): TCP-клиент §4.2.6 — Logon(1000) →
  MarketDataRequest(1002, ApplBegSeqNum..ApplEndSeqNum) → приём пакетов в
  формате Snapshot-пакета → Logout(1001) с подтверждением. Лимиты спеки
  вшиты: не больше 1000 сообщений за запрос, не больше 2 соединений
  одновременно, суточный счётчик соединений, обязательный ответ на
  Logout в течение 1 с.
- **`SnapshotAssembler`** (новое): по `SecurityID` копит фрагменты между
  `StartOfSnapshot` и `EndOfSnapshot`; потеря фрагмента (гэп `MsgSeqNum`
  snapshot-канала, который сбрасывается в 1 каждый цикл) — сброс
  частичного снапшота, ждём следующего цикла; собранный снапшот отдаётся
  целиком с `LastMsgSeqNumProcessed` и `RptSeq`.

### 2.2. `orderbook.Engine`

- Политика последовательности: `seq <= last` → `ErrDuplicate` (вызывающий
  игнорирует), `seq > last+1` → `ErrSequenceGap`; итоговое правило (+1 или
  только монотонность) фиксируется после pcap (N6). `Clear()` и явный
  `ResetSeq()` сбрасывают трекер.
- `ErrUnknownOrder` — не фатален: счётчик и, при превышении порога за окно,
  запрос ресинка; книга не стирается.
- Фильтр `NonQuote` — на уровне `forts/`, до движка (движок остаётся
  протокольно-нейтральным).
- Уровни: вместо `map + sort` на каждый вызов — отсортированные слайсы
  уровней с бинарным поиском (вставка O(log n) с memmove, чтение топ-N O(N));
  `TopN(side, dst []Level) []Level` пишет в буфер вызывающего. Тонкость: у
  FORTS книги неглубокие, дерево не нужно; если профиль покажет обратное —
  B-tree за тем же API.
- Best bid/ask — из головы отсортированного слайса, кэш и пересчёт
  исчезают.

### 2.3. `forts/` — сессия книг вместо `WatchOrderBook`

`BookSession` на N инструментов с одним `Feed` и машиной состояний на
инструмент: `Collecting` (копим инкременты в кольцевой буфер по
`MsgSeqNum`) → `Syncing` (ждём собранный снапшот; на `EndOfSnapshot`:
`LoadSnapshot(RptSeq)`, применяем из буфера только пакеты с
`MsgSeqNum > LastMsgSeqNumProcessed`) → `Live` → при гэпе `Recovering`:
если гэп ≤ 1000 пакетов и Replay настроен — Replay и наложение
(дубликаты отбрасываются по N5), иначе — обратно в `Syncing` только для
инструментов с разрывом `RptSeq`. `SequenceReset` → сброс трекеров и
ожидание `RptSeq = 1`. EmptyBook по таблице §4.2.8 (глобальная чистка,
затем книги приезжают как OrderUpdate с `PossDupFlag`); вариант §4.2.2
реализуется по результату pcap (N7).

Выход для ядра — колбэк `OnBook(securityID, *Engine, seq)` на
read-горутине (ноль аллокаций, потребитель читает `TopN` в свой буфер);
канал с копиями уровней остаётся как адаптер для не-hot потребителей.

## 3. Этапы

Порядок важен: этап 0 — предпосылка для всего остального, потому что
именно он отвечает на N6/N7 и ловит V1/V2/N1, которые синтетические тесты
пропустили.

### Этап 0. Полигон на официальных pcap (1–2 дня) — ВЫПОЛНЕН 02.09.2026

- Скачать с `ftp.moex.com/pub/SIMBA/Spectra/prod/pcap/` (это прод-трафик,
  выложен биржей публично): для начала `SIMBA-2026-05-15_0439_0450.zip`
  (176 МБ: SequenceReset + полный EmptyBook — закрывает N3/N7) и
  `SIMBA-2026-05-15_0959_1005.zip` (197 МБ: старт основной сессии). Полный
  набор ≈ 2.6 ГБ, тянуть по мере надобности.
- Написать читалку pcap без cgo и без зависимостей: формат pcap — 24 байта
  глобального заголовка + 16 байт на запись, снятие Ethernet/IPv4/UDP —
  ~50 строк. Фильтр по группе/порту из `configuration.xml`; отдельно
  проверить, есть ли в дампе обе ноги A/B.
- `cmd/simba-replay` (или тестовый хелпер): прогон датаграмм через декодер
  и `BookSession`, инварианты: (а) нет необъяснённых гэпов `MsgSeqNum` в
  дампе; (б) **книга, собранная из снапшота + инкрементов, побайтово равна
  следующему снапшоту того же инструмента** — главная проверка
  корректности; (в) доля пакетов с ≥2 сообщениями, распределение размеров;
  (г) факты по N6 (непрерывность `RptSeq`) и N7 (что окружает EmptyBook).
- Вырезать из дампов маленькие фикстуры (единицы МБ) и положить в
  `internal/simba/testdata/` вместе со схемой XML — golden-тесты живут в
  репо, полные pcap — нет.

### Этап 1. Декодер (1 день) — ВЫПОЛНЕН 02.09.2026

Цикл по сообщениям в пакете (V1), guard схемы/размера (N8), value-типы и
итерация групп без аллокаций (V4, часть), `AllocsPerRun == 0` в тестах.
Тесты: пакет из §4.2.1 (OrderUpdate + 2×OrderExecution), пакет из §4.2.2

### Этап 2. Снапшот и синхронизация (3–4 дня) — ВЫПОЛНЕН 02.09.2026

Collecting/Live, буфер позднего подключения с лимитом, сборщик

гэпу RptSeq, snapshot-листенер по требованию, счётчики `Stats()`);

### Этап 3. Надёжность (2–3 дня) — ВЫПОЛНЕН 02.09.2026
