Инструмент: `cmd/simba-replay` (этот репозиторий). Данные: официальные
записи прод-трафика с `https://ftp.moex.com/pub/SIMBA/Spectra/prod/pcap/`
(локально `~/artefacts/moex-pcap/`):

| Дамп | Окно (UTC) | Что внутри |
|---|---|---|
| `SIMBA-2026-05-15_0439_0450` | 01:41–01:50 (04:41 МСК, техперерыв) | SequenceReset, полный EmptyBook, перевыставление книг |
| `SIMBA-2026-05-15_0959_1005` | 06:59–07:05 (09:59 МСК, старт основной сессии) | 6 минут живого потока |

## 1. Главный результат: эталонная модель книги совпадает с биржей

Наивная модель (`cmd/simba-replay/verify.go`: map заявок, применение
инкрементов по правилам спеки, синхронизация со снапшотом по
`LastMsgSeqNumProcessed`) проверена двумя оракулами:

| Оракул | Основная сессия | Техперерыв |
|---|---|---|
| Снапшот == книга после применения инкрементов с `MsgSeqNum ≤ L` | 291 415 сравнений, **0 расхождений** (6929 инструментов) | 648 583 сравнения, **0 расхождений** (2770 инструментов; книги собраны из перевыставления после EmptyBook) |
| BestPrices == лучшие уровни книги после конца транзакции | 13 094 проверки, **0 расхождений** | нет сделок |
| `RptSeq` снапшота == `RptSeq` книги в точке L | 0 расхождений | 0 расхождений |
| Delete/Change по неизвестной заявке | **0** | 0 |

Значит, семантика ниже — не гипотеза, а подтверждённый контракт, на
который можно писать движок и тесты.

## 2. Ответы на вопросы плана (раздел 4)

**N6 — непрерывность `RptSeq`.** Строго непрерывен: 2 168 068 переходов
внутри инструментов, все с шагом ровно 1, если считать **все** сообщения
OrderUpdate и OrderExecution, включая технические сделки и NonQuote.
Если технические сделки (OrderExecution с `MDEntryPx = null`) выкинуть
до учёта, появляются «дыры» (2755 шагов по 3, единичные 5/7/13). Пример
из спеки §4.2.1 с 60142 → 60144 — именно такая дыра. Вывод для движка:
**фильтровать по NonQuote/технической сделке надо после продвижения
счётчика `RptSeq`, а не вместо него.** Текущий `applyOrderExecutionDelta`
выходит до движка на null-цене и не двигает `lastSeq` → следующее
сообщение даёт `ErrSequenceGap` → `Clear()`. В основной сессии таких
сообщений 5564 за 6 минут, то есть книга стиралась бы ~15 раз в минуту.

**N7 — EmptyBook внутри транзакции (§4.2.2).** За 6 минут основной сессии
при 2.1 млн обновлений и 4215 активных инструментах — **ни одного
EmptyBook**. Единственный EmptyBook в дампах — глобальный, из техперерыва:
сразу после `SequenceReset(NewSeqNo=1)`, отдельным пакетом,
`ExchangeTradingSessionID = null`, `LastMsgSeqNumProcessed = 0`, ровно как
§4.2.7. Пункт можно закрыть как «глобальная чистка по §4.2.8»; вариант
§4.2.2 если и существует, то настолько редок, что в план не входит
(поймать можно только вечерним дампом `2349_0030` с клирингом — там
EmptyBook «с непустой сессией»).

**Схема на проводе — версия 8, не 9.** Все 2.7 млн SBE-заголовков в обоих
дампах: `SchemaID=19780, Version=8`. В info-потоках идут шаблоны **21**
(SecurityDefinition) и **9** (SecurityStatus), которые в 9.0 стали 27 и
28. Код v1.0 ждёт 27 → `ResolveSecurityID` на таком фиде не найдёт ни
одного инструмента и молча отвалится по таймауту. Схема 9.0 выложена на
FTP 22.06.2026, дампы от 15.05.2026; какая версия в проде сегодня —
неизвестно. Декодер обязан проверять `Version` и знать таблицу id для
обеих (пункт N8 плана поднимается до обязательного).

## 3. Что ещё показал провод

### Инкрементальный поток (основная сессия, 6 минут)

- 1 256 745 пакетов, 3500 пакетов/с в среднем; `MsgSeqNum` без единой
  дыры и дубля.
- **67.8 % пакетов содержат больше одного сообщения**: до 20+ сообщений,
  payload до 1400 байт. 13 808 пакетов с `LastFragment = 0` (транзакция
  не влезла в MTU). Дефект V1 плана (читается одно сообщение) терял бы
  две трети потока.
- Состав: OrderUpdate 2 116 141, OrderExecution 56 142, BestPrices 12 300.
- **OrderUpdate: только New (1 077 214) и Delete (1 038 927), ни одного
  Change.** Изменение заявки на проводе — это Delete + New.
- OrderExecution: New 5564 (все — технические сделки с null-ценой и
  флагом NonQuote), Change 21 552, Delete 29 026; Active = Passive = 28 071
  — каждая сделка даёт ровно пару сообщений (агрессор + пассив).
- Агрессивная заявка всегда сначала приходит как OrderUpdate New (даже
  IOC) и только потом исполняется: 0 неизвестных заявок у модели. То есть
  `ErrUnknownOrder` в корректно синхронизированной книге — признак
  рассинхрона, а не штатная ситуация; стирать книгу на нём нельзя, но и
  игнорировать молча тоже.
- NonQuote-заявок (OTC) в потоке 0; в снапшотах 0. Фильтр §4.2.9 нужен
  «для порядка», на этих данных он ничего не меняет.
- BestPrices приходит **до** пакетов с изменениями заявок и описывает
  **итоговое** состояние после транзакции; `MktBidPx = null`, если сторона
  пуста. Проверять его можно по флагу `EndOfTransaction` последнего
  сообщения.

### Снапшот-поток

- Цикл **7.6 с** (основная сессия, 5972 инструмента, ~11 900 пакетов за
  цикл) и **2.3 с** в техперерыве (2770 инструментов). Цикл начинается с
  `SequenceReset(NewSeqNo=1)` последним номером старого цикла, следующий
  пакет идёт с `MsgSeqNum = 1`.
- **Все снапшоты одного цикла несут одинаковый `LastMsgSeqNumProcessed`** =
  номер инкрементального пакета в момент старта цикла. Снимок делается
  один раз на цикл и потом 7.6 с рассылается.
- Отсюда **лаг снапшота до 51 132 пакетов** (~15 с трафика) относительно
  живого потока к моменту получения `EndOfSnapshot`. Буфер накопления
  инкрементов при позднем подключении должен держать не меньше ~60 000
  пакетов (около 8 МБ сырых payload) — иначе склейка по §4.2.5
  невозможна. У модели максимум ожидающих сообщений на один инструмент —
  32 794.
- Фрагментация: **до 323 пакетов на один инструмент** (по 23 записи в
  пакете, ~7400 заявок в книге). 91 % инструментов влезают в один
  пакет, но хвост длинный. `StartOfSnapshot`/`EndOfSnapshot` стоят на
  первом/последнем пакете инструмента; фрагменты одного инструмента идут
  подряд.
- Пустая книга в снапшоте — одна запись с `MDEntryType = 'J'` и
  `MDEntryID = null` (2905 таких за 6 минут).
- **`RptSeq = 0` в снапшоте** у инструментов, по которым с момента
  суточного сброса не было ни одного обновления (56 969 снапшотов за 6
  минут основной сессии; все 648 583 в техперерыве).

### Техперерыв (суточный сброс, §4.2.7)

Последовательность на проводе: `SequenceReset(NewSeqNo=1)` в пакете с
`MsgSeqNum = 1` → `EmptyBook(LastMsgSeqNumProcessed = 0)` **тоже в пакете с
`MsgSeqNum = 1`** (пакет SequenceReset нумерован уже в новой
последовательности, а следующий за ним пакет несёт `NewSeqNo` ещё раз;
после миллионных номеров клиент, проверяющий дубликаты до разбора
сообщения, отбросит сам SequenceReset), `ExchangeTradingSessionID = null`,
`TransactTime = 0` → дальше 2, 3, … →
1989 пакетов OrderUpdate New с флагом **`PossDupFlag`** и **`LastFragment
= 0`** (всё перевыставление — одна гигантская «транзакция», последний
пакет с `LastFragment = 1`), 45 755 заявок по 2768 инструментам.

**У всех перевыставленных заявок `RptSeq = 0`** (42 987 переходов, все с
дельтой 0). Клиент обязан принимать такие обновления без проверки
последовательности; первое реальное обновление после этого должно
прийти с `RptSeq = 1` (в дампе торговли не было — проверить на дампе
`0849_0905`). Книги, собранные из этого перевыставления, совпали со
снапшотами по всем 2770 инструментам. Текущий движок на этом сломается:
после первой заявки с `rpt=0` вторая с `rpt=0` даст `ErrSequenceGap`.

## 4. Что это меняет в плане

Добавляются дефекты:

- **N13.** Технические сделки и любые фильтруемые сообщения обязаны
  продвигать `RptSeq` (см. N6 выше). Сейчас — нет.
- **N14.** Перевыставление после EmptyBook идёт с `RptSeq = 0` и
  `PossDupFlag`; движку нужен режим «загрузка без проверки
  последовательности» до первого обновления с `RptSeq ≥ 1`.
- **N15.** Прод в мае 2026 был на схеме 8 (шаблоны 21/9 вместо 27/28).
  Нужна таблица id по версиям и жёсткая проверка `Version` (N8 из
  «желательно» переходит в «обязательно»).

Закрываются как решённые: N6 (строгий +1 по всем сообщениям), N7
(EmptyBook — глобальная чистка; §4.2.2 в план не входит).

Уточняются размеры: буфер позднего подключения ≥ 60 000 пакетов;
сборщик снапшота должен переживать 323 фрагмента на инструмент; ожидать
~6000 инструментов в цикле и до 5 сообщений на пакет в типичном случае.

## 6. Как воспроизвести

```bash
go build -o /tmp/simba-replay ./cmd/simba-replay
/tmp/simba-replay flows  -pcap ~/artefacts/moex-pcap/SIMBA-2026-05-15_0959_1005.zip
/tmp/simba-replay stats  -pcap ~/artefacts/moex-pcap/SIMBA-2026-05-15_0959_1005.zip -examples 8
/tmp/simba-replay verify -pcap ~/artefacts/moex-pcap/SIMBA-2026-05-15_0959_1005.zip
/tmp/simba-replay extract -pcap ... -sec 7299709,3416766 -from 3s -to 26s -out fixture.pcap.gz
go test ./cmd/simba-replay/   # golden-тест оракула на testdata/*.pcap.gz
```

Дамп на 800 МБ прогоняется за ~5 с при ~100 МБ RSS: zip читается
потоково, ничего не распаковывается на диск. Группы по умолчанию — прод
«primary» (A) из `configuration.xml`; для других контуров задавать `-inc`
и `-snap`.

Фикстуры в `internal/simba/testdata/` вырезаны командой `extract`:
`main-session-2instr` (инструменты 7299709 и 3416766, 3 снапшот-цикла,
13 транзакций со сделками) и `tech-break-2instr` (SequenceReset,
EmptyBook, перевыставление, 4 цикла). При вырезании `MsgSeqNum`
перенумерован, `LastMsgSeqNumProcessed` пересчитан — фикстуры
самосогласованны и годятся как вход для будущего клиента, не только для
эталонной модели.
